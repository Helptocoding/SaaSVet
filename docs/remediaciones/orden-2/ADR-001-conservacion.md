# ADR-001 — Conservación de sujetos y borrado excepcional

Fecha: 28–29-10-2026. Revisión de base: `8886604`. El grafo codebase-memory no está conectado (recursos y plantillas MCP vacíos): cada relación y lector se contrastó en los modelos, vistas, servicios y migraciones actuales. No se toman líneas del índice antiguo como prueba de ausencia.

## Política de datos, por FK

| Relación | Política implementada y consumidor |
|---|---|
| `InvoiceAuditLog.invoice` | **PROTECT**, factura nunca es objetivo físico. `invoice_public_id` se captura en writer y se reconstruye desde la factura existente en `billing.0036`; auditoría y factura sobreviven. El SET_NULL del backlog antiguo no era apropiado para esta política. |
| `Prescription.medical_record` | **PROTECT**; receta/expediente conservados. Borrado de `Prescription` por collector también bloqueado. `PrescriptionItem` no se elimina por borrar un sujeto. |
| `StockMovement.product` **y** `.presentation` | **PROTECT** en ambos; ledger, unidades, cantidades y anclas no cambian al intentar borrar ninguno. `Product` y `Presentation` no son targets físicos. |
| `OrganizationTimezoneAudit.organization` | **PROTECT**; evento de zona horaria e identidad tenant permanecen. También `OrganizationStateAudit.organization` PROTECT; ninguna auditoría se purga para calificar una clínica como vacía. |
| `MedicalRecordProduct.medical_record`, `MedicalRecordService.medical_record`, `VitalSigns.medical_record` | **PROTECT**; sumado al guard `pre_delete` del expediente cerrado/con contenido/cargos/movimientos/Checkout. Un borrador abierto sin evidencia conserva el DELETE clínico existente. No hay restock por archivar ni por borrar padre. |
| `Pet.owner` y `PetRegistrationEffect.owner/.pet` | **PROTECT**. Un Owner con cualquier Pet existente no se borra. Procedencia del agente, metadata de importación (`legacy_id`/`extra_data`), auditoría genérica de Django admin y demás referencias no soportadas son blockers; no modificar consentimiento/autoridad. |

El ORM directo está guardado por `pre_delete`. Los lectores de detalle, PDF, serializers e historial usan identidad conservada; links `*_public_id` de escritura pasan a NULL para sujetos archivados/eliminados. |
| `Appointment.pet`, `VaccineRecord.pet`, `ConsultationAssessment.pet`, `SurgeryRecord.pet`, `EmergencyRecord.pet` y relaciones de agente | **Bloquear borrado físico si existen**, incluso eventos terminados. | `Invoice.appointment/.medical_record`, `StockMovement.invoice/.medical_record` | SET_NULL preexistente, pero Invoice no se elimina, MR con evidencia conserva su fila. La API excepcional no borra estas entidades. |

La provisión habitual crea singleton, genéricos y roles; una clínica así no es vacía. `Organization` con historia se desactiva y su staff pierde acceso. |

## Identidad de documento

`subject_snapshot` v1 en Invoice, Checkout, MedicalRecord y Prescription contiene UUID de organización, UUID/nombre de cliente, teléfono (solo PDF existente), UUID/nombre/especie/raza de mascota (PDF/documento), sexo/fecha de nacimiento (filtros de recetas y summary), `source` (`captured`, `reconstructed`, `unknown`) y `recorded_at` real. Se captura al crear documento; backfill `billing.0039` reconstruye únicamente lo disponible **en ese momento**. Renombre no actualiza snapshot. PostgreSQL `billing.0041` verifica tenant/UUID de sujetos presentes, procedencia e inmutabilidad, incluido bypass SQL; UUID públicos de padres son inmutables en DB. UUID histórico se expone separado del selector vivo. Un snapshot anterior que carezca de atributos requeridos bloquea la excepción física.

El expediente cerrado usa `vet_public_id_at_close`, `vet_name_at_close`, `vet_specialty_at_close`, `vet_snapshot_source`, `vet_snapshot_recorded_at`. El servicio de cierre captura primer cierre; replay no reescribe. `medical_records.0026` reconstruye desde usuario actual cuando tiene nombre y tenant correcto, con fecha real de reconstrucción; sin fuente conserva `unknown`, sin atribución falsa al instante `closed_at`. El lector de expediente cerrado usa snapshot, no el nombre mutable del usuario.

## Orden transaccional y DB

- Archivo y creación manual/automática: **Organization → Owner → Pet por PK**. La creación de citas ya compartía esos locks; la creación HTTP de consultas, `patients.creation` y la materialización del importador validan actividad bajo ellos. Archivo comprueba toda cita scheduled/confirmed/in_progress incluso pasada y toda consulta open, antes de mutar Owner o Pet. Restaurar Owner no restaura Pet. Facturas posted pueden cobrarse después del archivo.
- Cierre: claim de receipt → lock MedicalRecord → validaciones por protocolo → materialización → snapshot de vet + `closed_at` → cita → Checkout primario → receipt, dentro de atomic. No se crea Invoice legacy. Tests dirigidos cubren replay y fallo de validación; no se atribuye una prueba de todas las intercalaciones a tests que no corrieron.
- Tenant: claves únicas `(id, organization_id)` en Owner/Pet/Appointment/MedicalRecord/Checkout y FKs compuestas Invoice/Checkout en PostgreSQL (`billing.0038`), triggers de nuevos Checkout e Invoice, y trigger de snapshot. Cobros de Checkout ya abierto se permiten aun con Owner archivado; un Checkout nuevo no. Una nulificación posterior no habilita una Invoice nueva sin Checkout/cliente.
- Organización: `is_active` con motivo/actor/fecha y auditoría. Login/refresh/JWT previos y sesiones Django comprueban estado; `agent.durable` y `agent.sender` bloquean nuevas admisiones; sender mantiene pending si nunca fue admitido. Reactivación no cambia staff ni flags de autonomía. Una salida ya admitida remotamente no se promete revocable ni se reintenta a ciegas.

## API física

Solo `IsPlatformOperator` (autenticado, superuser, staff, ADMIN_SAAS). `POST /api/platform/physical-deletions/preview/` valida `target_type` cerrado (`owner|pet|organization`), UUID objetivo/organización y motivo de 8–255 caracteres. Devuelve `eligible`, blockers codificados, conteos de impacto y confirmación firmada si elegible. Confirmación incluye actor, tenant, target, acción, motivo y digest de relaciones; TTL **300 segundos**. `POST /api/platform/physical-deletions/execute/` exige el mismo payload, confirmación y UUID idempotency_key; reautoriza y revalida bajo lock de organización/objetivo. Stale/conflicto: 409 sin mutación; falla de auditoría revierte nulificación y DELETE. `PhysicalDeletionReceipt` guarda actor/rol, UUID lógicos, motivo, operación, resultado, fecha e impacto **sin FK al target**. Replay de key/payload vuelve al recibo después de autorizar actor y scope, aunque ya no exista el target; key diferente con confirmación consumida se rechaza. `pre_delete` impide bypass de instancia/queryset/collector por rutas normales. Organización realmente vacía/desactivada se puede eliminar; una provisionada no se vacía automáticamente para conseguirlo.

La API conserva historia, no anonimiza ni ofrece borrado total. Referencias no soportadas bloquean con `unsupported_reference`; procedencia de importación no modelada en snapshot bloquea con `unsupported_import_provenance`. No se relajan constraints para forzar éxito. Reversión de código no recupera filas físicamente borradas; migraciones que vuelven a exigir FK no nula no son seguras tras separación real. La reversión de `billing.0041` antes de borrados físicos se comprobó solo en el clúster aislado.
