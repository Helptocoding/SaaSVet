# ADR p60 — implementación de los cursores de WA-PERF-03

Fecha: 2026-10-21. Estado: implementado y verificado localmente como detalle de
D-5 del [ADR p60](2026-08-22-p60-whatsapp-inbox-decisions.md). El despliegue y los
gates operativos permanecen pendientes; SSE conserva su NO-GO y p61 sigue reservado
a una eventual reapertura de esa decisión.

## Decisión

Los GET completos de lista y transcript reciente emiten `sync_cursor`. El cursor
firmado pertenece a organización, usuario y recurso/consulta: lista con sus
filtros efectivos y offset, o un par contacto/cuenta. Incluye watermarks del
servidor `(updated_at,id)` y referencia un snapshot inmutable de fingerprints
en el caché `default` existente, con TTL de diez minutos. No usa reloj del cliente
ni consume el snapshot al consultar: pestañas concurrentes y replays son seguros.

El snapshot conserva hashes, IDs, orden y límites de lectura; no cuerpos, nombres
ni teléfonos. No es autoridad de negocio. Caducidad, firma/scope inválidos o pérdida
de caché producen el error canónico `400 invalid_sync_cursor`; la UI recupera la
vista completa y continúa con un cursor nuevo. Si no puede guardar un snapshot,
el GET completo sigue disponible con `sync_cursor=null`. No hay nuevas tablas,
aliases, servicios, secretos ni un scheduler de limpieza.

Los watermarks se complementan con fingerprints y pertenencia. Un corte estricto
por max(updated_at,id) puede omitir commits tardíos, dos cambios del mismo registro
con igual timestamp, retiradas o la expiración de un lease sin escritura. La lista
recalcula su proyección paginada optimizada y compara hashes; el transcript calcula
en SQL fingerprints del rango cargado, incluyendo updated_at, ID y los campos
publicados. Solo materializa cuerpos de mensajes modificados/nuevos. El preview
de conversación se limita a 120 caracteres en SQL y reutiliza el prefetch existente.

El backend firma también `sync_floor`, límite de lectura por usuario/hilo emitido
en páginas recientes/anteriores/centradas. La UI lo devuelve como `floor` al hacer
delta o recuperación. El límite sigue siendo válido si su fila desaparece y
permite ampliar el historial sin depender de un timestamp aportado por el cliente.
Al ampliar el rango se envían sus IDs visibles para reconciliar filas que hubieran
desaparecido durante una carga anterior. `before`/`around` siguen siendo canales
independientes y no admiten `since` simultáneo.

## Escrituras y compatibilidad

Cinco modelos optan por mantenimiento central de `updated_at`: Message,
Conversation, ContactIdentity, HumanHandoff e InboxReadState. Cubre save parcial,
update atómico y bulk_update, incluidos managers sin filtros. Se conservan
predicados, locks, validación, default manager y aislamiento tenant; los otros
dominios no optan por este comportamiento. No cambia ningún guard, epoch,
transición ni evidencia B4. El inventario y las regresiones están en la evidencia.

El frontend guarda un cursor por página y publica juntas las páginas cargadas.
Los deltas se combinan por hilo/ID y aplican retiradas explícitas. Hay una petición
activa por recurso; cambiar hilo/filtro aborta la anterior. «Cargar más» interrumpe
el poll de fondo pendiente. Los relojes visibles y la pausa por visibilidad se
conservan; volver a la pestaña intenta delta. Un paquete inconsistente se recupera
por GET completo, manteniendo el rango leído, borrador y ancla.

## Coste y validación

El coste SQL sigue siendo proporcional a la página/rango cargados. Esta decisión
reduce transferencia; no convierte los GET en un changefeed ni acredita capacidad
comercial. En PostgreSQL, 6.001 mensajes con 50 cargados producen 52.002 bytes en
full y 303 en delta estable (JSON sin compresión HTTP, 99,42 % menos). EXPLAIN usa el índice existente
`(organization,contact,channel_account,created_at)` para 50 filas; no se justifica
otro índice ni migración. Se registra el plan completo, sin fijar umbrales de tiempo.

[Evidencia y límites](../evals/inbox-perf-03-2026-10-21/README.md): 123 pruebas API y
259 frontend únicas PASS en evidencia compuesta, build/lint/drift y Chromium
escritorio/móvil PASS. M3 permanece sin aplicar a la base de trabajo. No se acredita
recepción real, Meta, media ni una nueva aceptación B9.
